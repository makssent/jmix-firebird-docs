= Example of Migrating an Application to Firebird

This section describes a real-world migration of an existing Jmix application from HSQLDB to Firebird. It uses the B2B CRM from the Jmix Demo collection as its basis. The migrated application is published in the https://github.com/makssent/jmix-crm-firebird[jmix-crm-firebird^] repository.

The migration was performed in stages: the add-on and JDBC driver were added to the original application, then the existing changelogs and test environment were adapted. The first startup with an empty database revealed two additional problems. After they were resolved, the application started successfully and the automated test suite passed with a Firebird datasource.

[[source-application]]
== Original Application

The application selected for migration was the https://github.com/jmix-framework/jmix-crm[official B2B CRM^], a full-featured demo application based on Jmix 3.0.1 and Java 21. The original state corresponded to commit `e4e31cd4cfb2906fa881434ebabb717592acb187` and used a file-based HSQLDB database as its primary data source.

The CRM includes customers, a product catalog, orders, invoices, payments, user tasks, analytics, and reports. The project also uses auditing, dynamic attributes, and other Jmix add-ons. Therefore, this migration tested the Firebird integration not only with a minimal application, but also with an extensive data model, user interface, and existing test suite.

[[connect-firebird]]
== Connecting Firebird

The first migration stage is recorded in the https://github.com/makssent/jmix-crm-firebird/commit/48d1c6e2c58bdbdcf6eb9468c36f54f73f0eeedb[`init firebird` commit^]. The HSQLDB dependency was replaced with the add-on starter and the Jaybird driver:

[source,groovy,subs="attributes+"]
----
implementation '{addon-group}:jmix-firebird-starter:{addon-version}'
runtimeOnly 'org.firebirdsql.jdbc:jaybird:{jaybird-version}'
----

The starter registers the Firebird implementations required by Jmix and EclipseLink, while Jaybird establishes the JDBC connection to the server. The driver is added separately because it is not included in the starter as a transitive runtime dependency.

In `application.properties`, the HSQLDB parameters were replaced with the settings for a prepared Firebird database. In addition to the JDBC URL and credentials, the driver and DBMS type had to be specified explicitly:

[source,properties]
----
main.datasource.url=jdbc:firebird://localhost:3050//path/to/b2b-crm.fdb?encoding=UTF8
main.datasource.username=sysdba
main.datasource.password=your_password
main.datasource.driver-class-name=org.firebirdsql.jdbc.FBDriver
jmix.data.dbms-type=firebird
----

The `jmix.data.dbms-type` property enables Jmix to select the implementations registered by the add-on. The existing `main.liquibase.change-log` property did not need to be changed: it already referenced the application's root changelog and was not part of the Firebird connection configuration.

These changes constitute the standard configuration of Firebird as the primary data source. For a complete description of the dependencies and properties, see xref:index.adoc#configuration[Connecting Firebird].

[[adapt-liquibase]]
== Adapting Liquibase

After changing the datasource, the existing CRM init changelogs had to be adapted for Firebird. The actual changes are collected in the https://github.com/makssent/jmix-crm-firebird/commit/213b0b3717eced383e9fefa3d0b5b4e2fcf22ff9[`init liquibase firebird` commit^].

First, the add-on changelog was included before the changelogs of the Jmix modules and the application. It defines Firebird-specific type property values. Next, in the entity initialization file, the literal `UUID` type of UUID columns was replaced with `${uuid.type}`. For changesets whose execution was already restricted by a list of DBMSs, `firebird` was added to the `dbms` attribute so that Liquibase would also create demo users and role assignments in the new database.

.Main configuration and Liquibase changes
[source,xml]
----
<!-- Root changelog: standard Firebird integration -->
<include file="/io/github/makssent/jmix/firebird/liquibase/changelog.xml"/>

<!-- CRM initialization file: adapting the existing schema -->
<column name="ID" type="${uuid.type}"/>

<!-- Firebird added to an existing CRM filter -->
<insert tableName="USER_"
        dbms="postgresql, mssql, hsqldb, firebird">
----

Thus, including the add-on changelog is part of the standard Firebird integration, while the `${uuid.type}` and `dbms` changes adapt the existing Liquibase files of this specific application. The general configuration procedure is described in xref:index.adoc#liquibase[Connecting Firebird], and the manual creation of subsequent changesets is covered in xref:liquibase-changelog.adoc[Creating a Liquibase Changelog].

[[migration-problems]]
== Problems Detected During Migration

After the initial configuration, the application did not complete its first startup with an empty database. The https://github.com/makssent/jmix-crm-firebird/commit/724d0a46f18aa9188a7e847e03fedf2fb74456f9[`fixed application startup with Firebird` commit^] contains solutions to two problems with different causes.

[cols="1,2,2",options="header"]
.Detected problems and their solutions
|===
|Source
|What happened
|Project solution

|`jmix-crm`
|`DynamicAttributesInitializer` accessed the `DYNAT_CATEGORY` table before Liquibase had finished on an empty database.
|An explicit `@DependsOn("jmix_Liquibase")` dependency was added to the initializer.

|Liquibase
|In the Liquibase version used, the `startValue` attribute of `createSequence` was rejected with the message `startValue is not allowed on firebird`.
|For Firebird, the sequence was temporarily created without `startValue`, followed by an `ALTER SEQUENCE ... RESTART WITH 1000` command.
|===

The first problem concerned the initialization order of the CRM's own components. It appeared while creating the schema in an empty database and is not a general Firebird limitation.

The second problem originated in validation performed by a third-party library. Splitting the changeset was a temporary workaround for the Liquibase version used, not a required part of connecting Firebird. A fix was proposed directly to Liquibase. For details and a link to the upstream PR, see xref:limitations.adoc#sequence-start-value[the description of the `createSequence` limitation].

[[adapt-tests]]
== Adapting and Running Tests

After the application was running on Firebird, the test environment was migrated to the same DBMS. In `application-test.properties`, the HSQLDB datasource was replaced with a Firebird datasource, and the test setup was changed to delete the old test database file before each new run. This allowed Liquibase to recreate the schema and the tests to run through a Jaybird connection.

Cleaning test data also required adding `onDelete="CASCADE"` to the self-referencing foreign key of the categories. This change is related to the hierarchical `Category` model and the data cleanup implementation in `jmix-crm`; it is not a general Firebird requirement. The complete test environment adaptation is available in the https://github.com/makssent/jmix-crm-firebird/commit/dff13455a8ec6cc8acbf0e16701d3deeebbaa251[`adapt tests for Firebird` commit^].

[[migration-result]]
== Migration Result

After these changes, the B2B CRM could be started and used with Firebird. Liquibase created the schema in an empty database, the application connected through Jaybird, the user interface opened, and the main CRM functionality worked. The application data model and core business logic did not need to be rewritten for the migration.

The changes fall into several categories:

[cols="1,2",options="header"]
|===
|Category
|Changes

|Standard Firebird connection
|Add-on starter, Jaybird, datasource, explicit DBMS type, and add-on changelog

|Existing project adaptation
|`${uuid.type}`, additions to existing `dbms` attributes, and a Firebird datasource for tests

|Fixes specific to `jmix-crm`
|The startup order of `DynamicAttributesInitializer` and cascading category deletion during test data cleanup

|Temporary third-party library workaround
|Creating a sequence without `startValue`, followed by a separate `ALTER SEQUENCE`
|===

The primary confirmation of the result was the full CRM test suite running with a Firebird datasource: 359 tests were executed, 26 were skipped, and there were no failures or errors.

[[summary]]
== Summary

This real-world migration demonstrated the path from an existing `jmix-crm` application on HSQLDB to a working application on Firebird. Most of the work involved dependencies, datasource configuration, and Liquibase adaptation. In addition, the initialization order of a specific CRM component and the test environment setup were corrected.

The migration history consists of four consecutive commits:

* https://github.com/makssent/jmix-crm-firebird/commit/48d1c6e2c58bdbdcf6eb9468c36f54f73f0eeedb[`48d1c6e`^] — connecting Firebird;
* https://github.com/makssent/jmix-crm-firebird/commit/213b0b3717eced383e9fefa3d0b5b4e2fcf22ff9[`213b0b3`^] — adapting Liquibase;
* https://github.com/makssent/jmix-crm-firebird/commit/724d0a46f18aa9188a7e847e03fedf2fb74456f9[`724d0a4`^] — resolving first-startup problems;
* https://github.com/makssent/jmix-crm-firebird/commit/dff13455a8ec6cc8acbf0e16701d3deeebbaa251[`dff1345`^] — adapting and running tests.

This result confirms that a full-featured Jmix application can be migrated to Firebird in the configuration examined here. It does not imply that other applications will not encounter additional considerations related to their data models or third-party libraries.
